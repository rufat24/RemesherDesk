# Testing and parity strategy

## 1. Test layers

| Layer | Where | Runs on | Framework |
|---|---|---|---|
| Unit | `tests/unit` | every CI job (`ctest -L unit`) | doctest (A2) |
| Property | `tests/property` | every CI job, 200 cases by default; `RDESK_PROPERTY_CASES=5000` locally | doctest + in-house generators |
| Tools | `tools/rdm`, `tools/unity/tests`, `tools/intake/tests` | `intake-tools` and `windows` jobs | Python stdlib, .NET 8, Pester-free PowerShell |
| Protocol conformance | `tests/protocol` | Linux and Windows | doctest, drives `rdesk` via `src/platform` |
| Fuzz | `tests/fuzz` | weekly, and PRs touching `src/io` | libFuzzer (clang) |
| Fuzz regressions | `tests/data/fuzz-regressions` | every CI job | ctest replay |
| GUI | `tests/gui` | Linux under xvfb; Windows uses `--selftest --no-gl` | controller unit tests + screenshot smoke |
| Parity **(B)** | `tests/parity` + `tests/golden` | Windows (reference) and Linux | `rdesk compare` |

## 2. Golden data

Golden data is captured in Unity with `tools/unity/MeshDump.cs` (procedure: `docs/intake.md` §2). Each case directory is laid out like this:

```
tests/golden/caseNN/
  before.rdm   after.rdm   after2.rdm (Unity re-run)   params.json (from COMP + user notes)
  boundary_in.rdm  boundary_out.rdm   (B, branch S/D: captured at the DllImport call)
  README.md   (what the mesh is, Unity version, Quadremesh version, timings)
```

Cases where you can predict the result exactly (for example a cube under the fake backend) live in `tests/data/` and are generated by scripts. They are not hand-edited.

## 3. Parity tiers and tolerances

Some notation:

- **d** is the bounding-box diagonal of the reference output.
- **ē** is its mean edge length.
- "Topology equal" means the same V, the same F, and identical connectivity, either in the same order or after canonical relabelling (faces sorted by their sorted vertex tuples, with vertices matched by exact position).

| Tier | When it applies | Requirement |
|---|---|---|
| **T0 bitwise** | The same binary on the same CPU, same thread count, same input bytes. Branch D on Windows; any branch for run-to-run determinism. | Output RDM `VPOS` and `SUBM` payloads are byte-identical (SHA-256 equal) across 5 runs, and against Unity's `after.rdm` if Unity itself was deterministic (`after` == `after2`). |
| **T1 near-exact** | Same algorithm, same compiler family and floating-point flags as Unity's build (branch S on MSVC with copied flags). | Topology equal **and** max vertex displacement ≤ **1e-5·d**. |
| **T2 statistical** | Different compiler, OS or libm (Linux gcc/clang vs the Windows reference; branch P vs Burst). | Two-sided Hausdorff ≤ **0.25·ē** and ≤ 1e-2·d; face count within ±2%; quad ratio within ±1 percentage point; irregular-vertex count within max(±10%, ±4); genus, component count and boundary-loop count **equal**; manifoldness and orientation flags equal. |

### Why these numbers

- **T1, 1e-5·d.** The float32 unit roundoff is 2^-24 ≈ 6e-8. Coordinates are bounded by about d, so one rounding step moves a coordinate by at most about 6e-8·d. 1e-5·d therefore allows roughly 170 rounding steps of accumulated drift. That covers contraction and summation-order differences across a few dozen smoothing iterations. The bound is still at least 100× below the edge length for any mesh with up to 1e6 faces, where ē ≳ d/√F ≥ 1e-3·d. So a T1 pass cannot hide a visibly different result.
- **T2, 0.25·ē.** A quad remesher makes discrete decisions: integer rounding, singularity placement, greedy orders. Floating-point noise can flip these, which changes local topology while keeping surface error and quality statistics similar. Measuring against the output edge length expresses "within a quarter of a quad" at any resolution. The cap of 1e-2·d keeps very coarse meshes honest. The ±2%, ±1 pp and ±10% bands are set so that typical quality noise passes and a systematic change, such as a different default parameter, fails.
- **Calibration (B3).** These are starting values. In B3, measure:
  1. Unity run-to-run (`after` vs `after2`).
  2. Our run-to-run (5 runs).
  3. Our Windows output vs Linux output.

  Then set each threshold to max(3× the observed maximum, the floor above), but never looser than the T2 caps. Record the measurements in `docs/parity-report.md`. Thresholds live in `tests/parity/tolerances.json`. Loosening any value needs a note in that report saying why.

### How Hausdorff is measured

1. Sample area-uniformly, N = max(1e5, 10·F) points per surface, plus all vertices. Use an in-house PCG32 with a fixed seed.
2. Compute exact point-to-triangle distance with an AABB tree.
3. Non-planar quads are split both ways and the minimum is used. This bias is at most the quad's non-planarity, which is reported.

## 4. Determinism concerns

Check each of these in the native code at intake, and avoid them in our own code:

| Source of non-determinism | Our code | Native code (B) |
|---|---|---|
| Thread scheduling (OpenMP/TBB reductions, atomics order) | single-threaded metrics | Note the threading model. T0 requires a fixed thread count, or a single thread (`--threads 1`) |
| RNG seeding (`rand`, `random_device`, time) | fixed-seed PCG32 | find seeds; expose a `seed` param if hidden |
| **`std::*_distribution` differs between libstdc++, libc++ and MSVC STL**, even with the same seed | not used | a cross-compiler bit-difference is expected → T2 |
| `std::sort` with equal keys: the order of equal elements differs by STL | `stable_sort` or total-order comparators | expected cross-STL difference → T2 |
| Iteration order of `unordered_*` | never feeds output order | expected cross-STL difference |
| Sorting or hashing by pointer address | forbidden | check |
| FMA contraction | `-ffp-contract=off` set in `cmake/RdeskWarnings.cmake`. GCC uses `off` already in ISO mode; clang's default `on` contracts within expressions. MSVC: `/fp:precise` | copy the original flags exactly (S1) |
| `-ffast-math` / `/fp:fast` | never | if the original uses it, T1 is only reachable with the same compiler |
| libm transcendentals (`sin`, `cos`, `exp`, `pow` are not correctly rounded and differ between glibc and UCRT) | avoided in comparison code | expected cross-OS difference → T2 |
| Burst `FloatMode`/`FloatPrecision` vs .NET JIT | — | branch P → T2 |

## 5. Property tests

The generators produce:

- subdivided platonic solids, tori (genus 1) and double tori (genus 2)
- random vertex perturbation
- random n-gon fan merges
- open patches with holes

All of them are seeded, and the seed is printed on failure.

**Properties every backend must satisfy** (the fake backend now, real backends in B3):

- output indices are in range and positions are finite
- no faces with fewer than 3 corners and no repeated corners
- orientation is consistent wherever the input was oriented
- genus and boundary-loop count are preserved for closed manifold input, if the backend claims it
- Hausdorff to the input ≤ a backend-declared bound
- determinism: two runs give identical bytes, if `caps.deterministic` is set
- the facade's convention round trip is transparent: same output whether the input arrives in RH or LH form, up to the exact conversion

**Properties of our own code:**

- reader(writer(m)) == m for RDM and OBJ
- `compare(m, m)` gives zero distance
- metrics are invariant under vertex relabelling

## 6. Fuzzing

- **Targets:**
  - `fuzz_rdm`: the whole reader
  - `fuzz_obj`: tinyobjloader plus our post-processing
  - `fuzz_params_json`: params parse and validation
  - `fuzz_protocol_line`: the GUI's event-line parser
- **Seed corpus:** every file in `tests/data` plus minimised crashers.
- **Rules:**
  - Allocation size must be bounded by the input size. Every reader checks this before it allocates.
  - `-rss_limit_mb=2048`, `-max_len=1048576`.
